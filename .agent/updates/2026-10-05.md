# 2026-10-05 更新：新增「知识库」（页面模块）

> 分支 `feature/knowledge-library`，模块版本 `19.0.1.11.0 → 19.0.1.12.0`。

## 一、定位：知识库是顶层空间，练习册是其中一个分类

- **知识库** = 每位登录账号自己的内容空间，1GB 配额，不限制内容类型；
- **分类**是条目上的一个字段（`workbook` / `leetcode` / `note` / `doc` / `other`），
  不是独立的模型树；练习册只是其中面向教辅的那一类；
- **练习册教材**通过委托继承落进知识库：每一份教材 PDF 都是
  `category=workbook` 的条目，占同一份配额、能被搜索和打标签、删除即释放；
- 教材仍保留自己的教学属性（`tutoring.workbook` 书名、全书页码区间、单页抽页缓存）。

## 二、数据模型

| 模型 | 作用 |
|---|---|
| `tutoring.library.item` | 知识库条目：user_id、category、name、tag_ids、content（bytea）、filename、file_size、upload_date、ext/mimetype/kind、preview_html |
| `tutoring.library.tag` | 标签字典，即输即建，逗号/顿号/分号分隔 |
| `tutoring.workbook.file` | 改为 `_inherits = {'tutoring.library.item': 'item_id'}`，正文与文件名归条目表 |

容量参数走系统参数（不写死）：`tutoring_center.library_quota_bytes`（默认 1GB）、
`tutoring_center.library_max_file_bytes`（默认 64MB）。

**64MB 单文件上限的由来**：Odoo 给每个请求体硬设 128MiB（`odoo/http.py`），
JSON-RPC 传二进制要先 base64 膨胀 1/3（实际顶到约 96MB），所以上传走 multipart
（`/tutoring/library/upload`），前端用 XHR 发 FormData，既拿到真实字节进度，
也不受膨胀影响；64MB 是留足余量的取值。

## 三、功能与交互

- **上传**：页面顶部常驻容量条 + 拖拽区，支持拖放与多选，逐个上传、逐条进度与结果；
  分类下拉与标签输入在上传时就带上；门户端是同一个模型的表单上传。
- **浏览**：看板（默认按分类分组的卡片墙）/ 列表 / 表单，搜索标题·文件名·标签，
  分类筛选与标签分组。
- **打开**：整卡或整行点击 → 页中页预览（PDF 与图片内嵌，其余给下载），
  改名、改分类、改标签、删除都在同一个弹窗里。
- **空状态**：动作 help 写清"怎么传、能传什么、容量多少"。
- **权限**：`base.group_user` 与 `base.group_portal` 都可读写自己的条目，
  record rule `[('user_id', '=', user.id)]`。
- **门户**：`/my/library`（上传+列表+容量条）、`/my/library/<id>`（预览+改名+删除），
  `/my` 首页新增知识库卡片与计数。

## 四、容量配额的统计方式与边界

- **统计口径**：`used_bytes()` 对该用户全部条目的 `file_size` 做 SQL 求和，
  只加数字、不读正文（Binary 列忌全量读）。`quota_state()` 给前端总量/已用/剩余/百分比。
- **删除**：正文在本表 bytea 列里，删行即释放，没有 filestore 残留
  （表空间的物理回收仍取决于 PostgreSQL 的 vacuum）。
- **并发**：`_lock_user()` 先 `SELECT ... FROM res_users WHERE id=%s FOR UPDATE`，
  把同一用户的"读已用 → 判剩余 → 写入"串行化；只锁这一个用户，不同用户互不阻塞。
- **超限拦截**：单文件超限与总量超限分开报错，文案里带上具体数字；
  服务端为准，前端另有一道预检（省掉一次白跑的上传）。
- **已知边界**：库内实际占用约为原始文件的 4/3（bytea 存的是 base64 文本），
  1GB 配额约对应 1.33GB 库体积；练习册教材计入上传者的配额。

## 五、迁移（`migrations/19.0.1.12.0/post-migrate.py`）

把 `tutoring_workbook_file` 的 `content` / `filename` 搬进新条目表、回填 `item_id`、
保留原上传时间，再把旧列 DROP 掉（ORM 不会因为字段消失而自动删列，不删就是两份额外副本）。
可重复执行。本机 3 份 53 教材（约 177MB）已迁入，抽页缓存不受影响。

## 六、新陷阱（接 2026-10-03 的 20~22，这里记 23~25）

23. **委托继承只搬"父有子没有"的字段**：`_inherits` 建父记录时，子模型已定义的
    同名字段不会传过去（本项目 `tutoring.workbook.file.name` 与条目 `name` 撞名），
    父表 NOT NULL 直接违反。父字段必须给默认值兜底，真实值创建后再同步。
24. **存储型计算字段要 flush 才落库**：`file_size` 这类 stored compute 的值在
    下一次 ORM flush 前，数据库列里仍是 NULL；用裸 SQL 求和会得到 0
    （表现："传了一堆文件，已用还是 0"）。统计方法里先 `env.flush_all()` 再查。
    另外 Binary 的 create 入参可能是 bytes 也可能是 str，算长度要两种都接。
25. **`@api.model` 方法不能拿记录调**：`record.tags_from_names(...)` 直接
    `AttributeError`，必须走 `env['model'].method()`。

## 七、验收状态

- 一次性新库 `zz_lib_check -i tutoring_center`：安装通过（19.0.1.12.0），
  委托继承、容量拦截、标签、删除释放、视图/动作/菜单/规则全部实测通过，验完已删库；
- 业务库 `OdooForDB`：已备份（198MB dump）+ 升级到 19.0.1.12.0，教材迁移核对无误；
- **尚未真机验收**：服务需管理员权限重启（UAC 提权被安全策略拦截），
  重启后需在浏览器中确认知识库页面、拖拽上传、容量条与门户页。

## 九、数据模型

- **`tutoring.library.folder`**：`name`（同用户内 `unique(name, user_id)`）、`user_id`（cascade）、
  `item_count` / `size_text` 两个计算字段各用**一次 `_read_group`** 取整列（不做 N+1）。
  单层，不做 parent_id——用户要的"分类当文件夹"够用。
- **`tutoring.library.item.folder_id`**：`ondelete='set null'`，删文件夹只把文件退回未分类，
  绝不动正文。**没写 `domain="[('user_id','=',user_id)]"`**：域里的 `user_id` 得在视图里存在，
  而记录规则本来就把下拉范围收成本人的，加域只会带来"字段不在视图里"的坑。
- **标签改成按用户私有**（这是本轮真正的隐私收口）：原来 `rule_library_tag_all` 是 `[(1,'=',1)]`
  全共享，标签名等于"这个人在学什么"，别人在 m2one 补全里就能看见。现在加 `user_id` +
  域改成本人 + `unique(name, user_id)`。`tags_from_names()` 的 search 天然只命中本人，代码没改。
  - xmlid **故意留着 `rule_library_tag_all` 这个名字**：组规则之间是 OR，改名会多出一条旧的
    全可见规则，靠升级清理去猜不划算（陷阱 17 同一个道理）。
  - 迁移 `migrations/19.0.1.13.0/post-migrate.py`：新列在存量行上必是 NULL，按"标签跟着用它的人走"
    回填；被多人用过的**拆成每人一份**（否则后一人改名会把前一个人的也改掉），没人用的孤儿删掉。可重复执行。

## 十一、这轮修掉的三个既有缺陷

1. `controllers/portal.py` 的 `/my/library/<id>/edit` 里用了未定义的 `model`
   （`NameError`）——门户点「保存修改」必 500。这就是"从未真机验收"漏下来的那条。
2. `_compute_preview_html` 原来用 `not item.content` 判空，**读一次预览就把整本 PDF 拉进内存**；
   改成看已落库的 `file_size`。
3. `/my/library/<id>/edit|delete` 原来 `browse().exists()` 再比 `user_id`：越权请求会先炸 500
   再被规则拦住（见陷阱 26）。改成 `search([('id','=',…)])`，别人那条直接是"不存在"→ 404。

## 十二、新陷阱（接 23~25，这里记 26~29）

26. **`browse(id).exists()` 与"已在 ORM 缓存里的字段值"都不经过记录规则**——`exists()` 是裸 SQL，
    而字段值命中缓存时不重新校验；同一个 shell 里先用甲读过这条记录，再切到乙读 `.name`
    照样返回真值。判"能不能碰"要用 `has_access('read')` 或 `search([('id','=',…)])`，
    别用 `browse().exists()` + 字段比较。
27. **SQL 约束炸过一次，整个事务就 aborted**，后面任何查询都是
    `InFailedSqlTransaction`。控制器里"先 `search_count` 查重再写"比"写失败再 rollback"干净；
    测试脚本要试失败分支得包 `with env.savepoint():`。
28. **顶栏菜单按登录态过滤有原生件**：`website.menu.group_ids` + 核心全局规则
    "Website menu: group_ids"（`website/security/website_security.xml`，
    `['|', ('group_ids','=',False), ('group_ids','in', user.all_group_ids.ids)]`）。
    菜单渲染前 `_compute_menu` 就按当前用户 search 过了，不用自己写模板条件；
    匿名（Public user 的 `group_ids` 是空的）自然看不到该项。
29. **门户页的 JS 不在 `web.assets_frontend.min.js` 里**——19 的网站壳加载的是
    `assets_frontend_minimal.min.js` + `data-src` 的 `assets_frontend_lazy.min.js`
    （后者 `('include', 'web.assets_frontend')`）。验收自己的前端代码进没进包，要 grep 的是
    lazy 那个 URL；只盯 `assets_frontend.min.js` 会误判成"没打包"。

30. **给存量表加 required 字段，别拿 `IS NULL` 找旧行**：Odoo 建列时把现有一行**预填成
    升级那一刻的当前用户**（业务库里两条标签就这么挂到了 `__system__` 机器人名下），
    于是"回填 NULL 行"的迁移一行都没改、日志还写着成功。判据要按业务事实重算
    （这里改成"标签跟着用它的人走"）。配套的另一半：**x2many/many2one 的目标被记录规则
    过滤掉时，读取是静默少行、不抛 AccessError**，所以表现是"徽章/下拉里悄悄少一项"，
    不是报错——只有把结果和库里的关系表对一遍才发现。

## 十五、部署时才暴露出来的两件事

1. **迁移的判断依据是错的，已改**：原来只挑 `user_id IS NULL` 的行，但 Odoo 给存量表加
   **required** 列时会把现有一行**预填成升级那一刻的当前用户**——业务库里两条标签直接变成
   `user_id=1`（`__system__` 机器人），迁移一行没改还"看起来跑成功了"。
   现在判据换成"拿条目重新核对"（归属不对就归位、被多人用过的拆副本、没人用的删掉），
   逻辑挪进 `tutoring.library.tag._assign_owner_from_items()`，迁移与一次性修数共用。
   业务库已用同一方法就地修好：`练习册v2` 归回 admin、`图片` 是孤儿已删。
   顺带量到一件好事：**x2many 的目标被规则过滤时，读取是静默少行、不抛错**——
   所以这个 bug 的表现是"标签徽章悄悄消失"而不是 500，没人会撞见（陷阱 30）。
2. **SVG 内联回吐是存储型 XSS 面**：`kind` 原来把 svg 算图片，
   `/tutoring/library/<id>/raw` 会以 `Content-Type: image/svg+xml` 内联返回，而 SVG 能嵌脚本。
   核心其实已经拦了非管理员（实测上传直接报"只有管理员可以上传SVG文件."），但管理员自己传仍会中。
   两头堵：`IMAGE_EXTS` 去掉 svg（预览区退化成下载按钮），raw 路由对 svg 一律按附件回吐
   + 补 `X-Content-Type-Options: nosniff`。纯 Python 变更，`restart odoo` 一次即生效。
